# AngelLive 斗鱼相关修复与双流移动端迁移研究

日期：2026-09-20。本次是源码对照和迁移规划，没有合并 AngelLive 代码、修改播放行为或构建移动端安装包。

审查基线：

- 本 fork：`0255cde502105e49e206d6a5602c9a5b75eb70d1`，分支 `feature/macos-decode-modes-20260912`，候选版本 `3.0.20+4108`。
- AngelLive：[`8cd8245d`](https://github.com/pcccccc/AngelLive/tree/8cd8245df981d4fc0cc54e628da26b1772f00a6a)，审查时的 main。
- 用户反馈：Mac 开启硬件解码后明显更流畅，卡顿基本消失。尚未确认使用“硬解 only”还是“硬解兼容”，没有同条件 CPU、掉帧率或功耗数据。这是用户实测反馈，不能外推为所有平台的性能结论。

## 1. AngelLive 修了什么，哪些适用于我们

### 弹幕：不额外发送服务器未要求的 Ping

[`9a432082`（2026-09-16）](https://github.com/pcccccc/AngelLive/commit/9a4320823f2768f745ba1e748f1e19cb8b7fcb4d) 删除宿主每 30 秒发送的 WebSocket control Ping，以及未收到匹配 Pong 就重连的判断。平台插件继续发送自己的应用层心跳。

其[验证记录](https://github.com/pcccccc/AngelLive/blob/8cd8245df981d4fc0cc54e628da26b1772f00a6a/docs/DanmakuConnectionRecovery.md)描述：额外 Ping 发出后约 50ms，服务器主动关闭连接；只保留插件心跳则持续正常。这是 AngelLive 提供的对照证据，记录没有公开具体平台名称，不能直接宣布 Pure Live 的斗鱼也是同一根因。其设备验证主要是 iOS 模拟器正常网络，不能当成我们的实机验证。

对照本仓库：

- [DouyuDanmaku](../lib/core/danmaku/douyu_danmaku.dart) 已经每 45 秒发送 `type@=mrkl/`。
- [WebScoketUtils](../lib/core/common/web_socket_util.dart) 没有配置额外的 WebSocket `pingInterval`，也没有匹配 Pong 的计时器。
- AngelLive 较早的 [`debd9622`](https://github.com/pcccccc/AngelLive/commit/debd9622314fed26a1bbf9d248d4c02a74101414) 将斗鱼心跳从 `keeplive` 改为 `mrkl`，我们也已具备。

**结论：不需要重复搬这两个心跳补丁。**

仍值得核查的是我们的通用静默超时：超过 `max(3 × 心跳间隔, 90s)` 没有任何入站消息就重连，斗鱼为 135 秒。这里计入所有收到的帧，不只是显示出来的聊天。如果服务器允许健康连接长期只发不收，这个判断可能误断；如果 `mrkl` 有可靠回应，它又能帮助发现半开连接。

目前没有真实入站记录证明发生了误判。后续先记录断开原因、距最后入站帧的时间、连接代次和心跳回应类型，再决定是否改为平台专属探活策略。保留用户要求的 **15 秒重试**；不通过取消所有超时来掩盖假连接。

### 弹幕重连：恢复意图不等于“当前已连接”

[`41be431d`（2026-09-06）](https://github.com/pcccccc/AngelLive/commit/41be431d4dcdd35ebeddc1cb271ad7c5279e77ea) 的可取之处：

- 心跳配置没变化时不重置计时，避免持续收帧把下一次心跳无限推迟。
- 旧连接和异步回调带会话代次，不能修改新连接。
- 显式退出才清除连接意图；断线或正在重连时切后台，回前台仍应恢复。
- 长时间网络中断后仍继续尝试，显式关闭取消计时和在途工作。

它当时也引入了后来撤掉的强制 Ping，因此不能整笔移植这个提交。

我们已经有代次隔离、握手失败恢复、关闭超时，以及持续 15 秒重试；心跳也不随每条消息重置。前台恢复由 [LivePlayController](../lib/modules/live_play/controllers/live_play_controller.dart) 触发，[DanmakuController.recoverRoomConnection](../lib/modules/live_play/controllers/danmaku_controller.dart) 会按当前选择的 A/B 来源恢复，而非仅检查之前是否已连接。已有 [WebSocket 回归测试](../test/web_socket_util_test.dart)覆盖握手失败、退出时迟到回调、持续重试和心跳流量。

**处置：保留当前机制，补移动端“断线中切后台 → 回前台”和 A/B 来源切换的组合验证；不重复引入另一套重连管理器。**

### 播放：直播 EOF 后先获取新地址

[`eed2d820`（2026-07-13）](https://github.com/pcccccc/AngelLive/commit/eed2d820791057fcc18d9b144f7f16859b414e6b) 是通用直播恢复修复，主要思路是：

1. 正在播放的直播出现 EOF/ended，进入恢复流程，而不是当作点播正常结束。
2. 恢复优先重新获取播放参数，再考虑换 CDN、重开旧 URL；避免持续重试已过期的签名地址。
3. 同一次结束触发的多个通知合并处理；连续稳定播放后才重置恢复次数。
4. 恢复保留画质和线路偏好，不顺带重建弹幕连接。

本仓库存在明确差异：

- [MediaKitAdapter](../lib/player/adapters/media_kit_adapter.dart) 转发 `completed`；[PlayerManager._bindPlayerStreams](../lib/player/core/player_manager.dart) 继续向外转发，没有发现 A 的直播 EOF 恢复消费者。
- `PlayerManager.retry()` 重开保存的 URL；错误恢复先使用现有线路列表，再按条件降级引擎，不等同于重新签名。
- B 的 [CommentarySyncController](../lib/modules/live_play/controllers/commentary_sync_controller.dart) 已监听完成事件，并在重连时重新解析来源；A/B 恢复能力并不对称。

**建议适配这个思路。** 它能解决一类“播放一段时间突然结束、旧地址重试无效”的问题；没有证据认定此前画面断续但声音连续也是 EOF。硬解改善的卡顿和这类网络恢复应分别验证。

实现边界：只处理已经起播、仍应播放的直播；用户暂停、切房、退出、录播正常结束不能触发。以会话代次合并 error/EOF；先刷新当前房间的播放地址并保持画质、线路选择，确认下播则停止重试。双流期间调用主流重载通知，恢复后重建基线、保留偏移，不能偷偷切成不支持同步的引擎。连续失败要有频率与次数约束及可见错误，不能形成无限快速刷接口。

### 公开代码的范围

AngelLive 当前把平台解析交给插件，审查的 main 树内没有斗鱼解析器源码。插件来源由用户配置；上述宿主提交不能证明外部斗鱼插件最新的签名、清晰度或 CDN 逻辑已经怎样修复。本次没有找到可以据此替换本仓库 `getH5PlayV1` 签名实现的新证据。

AngelLive 根目录许可证为 GPL v3，本 fork 为 AGPL v3。本次只研究行为和事件顺序；后续若复制具体代码，需要连同来源、版权和相应组件许可证一起核对、保留，不能仅凭宿主许可证推定外部插件许可证。

## 2. Android / iOS 已有基础与实际缺口

核心可继续用现有 MediaKit 和 Dart 控制器。Android 与 iOS 都具备可行性，但“代码能编译”或“显示了入口”不等于双流已经可用。

| 功能 | 可复用部分 | 移动端必须补的部分 |
| --- | --- | --- |
| A 画面 + B 声音 | 双槽播放器、B 最低画质懒解析、线路回退、音量恢复 | Android 开放前验证；iOS 处理默认 IJK 引擎；双流会话限制引擎降级 |
| 内容校准与防漂移 | 10/100/500ms、±30s、相对基线、倍速纠偏、重新同步 | 手机触摸布局、横竖屏、前后台恢复后重建基线 |
| A/B 弹幕选择 | 来源连接、延迟队列、断线重连 | 竖屏入口、后台后恢复当前来源、消息积压清理 |
| B 临时预览 | 同一个 B 实例开关视频轨 | 短视频区域放不下桌面校准小窗；Surface/纹理迁移 |
| 九点裁剪与覆盖 | 归一化坐标、确认/取消、拖动和缩放 | 更大的触摸命中区、与亮度/音量手势隔离、旋转后边界 |
| 播放/暂停/音量 | 系统媒体操作已经委托给双流控制器 | 系统播放状态仍取 A，需区分用户暂停与校准暂停；处理中断恢复 |
| 后台音频 | 现有 AudioSession、Android 前台服务、iOS audio background mode | 两路统一生命周期、视频资源暂停/恢复、基线失效处理 |
| 系统画中画 | Android 已有 Activity PiP | 当前紧凑画面不含 B 裁剪层；iOS 没有同等原生 PiP 实现 |

### 引擎是首要阻塞项

[CommentaryPlatformSupport](../lib/modules/live_play/service/commentary_platform_support.dart) 当前允许 macOS、Windows、iOS，不允许 Android。iOS 只是实验入口。

[播放器默认配置](../lib/common/services/settings/player_settings_controller.dart)在 iOS 选择 `ijk`；[FijkAdapter](../lib/player/adapters/fijk_adapter.dart) 没有实现 `SyncCapablePlayer`，而双流 `activate()` 在进入错误恢复块前就会拒绝不支持的主播放器。来源弹窗没有先切引擎，也未捕获这一前置异常。因此 iOS 默认配置存在“选了 B 仍不能启动双流”的代码路径。

建议在双流会话中确保 A 使用 MediaKit，并保存原引擎偏好。准备失败保持 A 可播放，成功后才接管双流；退出和切房按生命周期恢复原偏好。双流期间限制自动降级到 IJK/其他非同步引擎，或显式退出双流再降级；不能保留指向旧实例的同步引用。这样普通单流无需跟着改默认内核。

Android 现有 MediaKit 路径默认允许硬解，原生控制器使用 `auto-safe`，兼容模式使用 `mediacodec`；并非整个项目过去都在软解。Mac 的 `videotoolbox`/`videotoolbox-copy` 配置不能直接套到 Android。iOS 需确认 MediaKit 实际选择的 VideoToolbox 解码器和视频输出，而非只查看设置开关。

### 校准与覆盖的触摸界面

[现有校准预览](../lib/modules/live_play/widgets/commentary_sync_widgets.dart)最小宽 300、顶部偏移 96，适合桌面，但在手机竖屏短视频区域会严重挤占 A 画面。建议：

- 手机校准用专用视图：横屏并排 A/B，竖屏上下排列；保留两个时间戳可同时比较。调整区只展示一个步长选择和提前/延后按钮。
- iPad 按可用宽度选择并排或小窗，兼顾分屏；不根据“是 iOS”统一套手机布局。
- 同步、来源和弹幕设置用可滚动底部面板；校准状态条随播放控件显示/隐藏。
- [裁剪手柄](../lib/modules/live_play/widgets/commentary_video_overlay.dart)当前命中区域为 28，覆盖缩放手柄为 32；触摸版扩至至少 44–48 logical pixels，视觉圆点可以保持较小。编辑时暂时让出底层播放手势，保留取消/确认和恢复原位置。
- 转屏、iPad 分屏按视频实际显示区域换算坐标，保留黑边之外的有效图像裁剪范围；一个 B 原生画面只由一个展示位置持有，延续此前灰屏修复的约束。

10ms 是用户请求的调整步长，不是移动系统定时器、直播解码和音频输出能保证的实际 10ms 精度。仍由用户对照事件校准，不能承诺自动识别同一比赛时刻。

### 后台与音频中断不能照搬桌面行为

[LiveAudioHandler](../lib/player/core/live_audio_handler.dart)存在三个需要先修的接口问题：

1. 通知栏播放状态和后台保活只订阅 A 的 `onPlaying`。为了让 B 提前而临时暂停 A 时，会把整个会话显示成暂停；Android 的 `androidStopForegroundOnPause: true` 还可能影响服务保活。应发布会话级播放状态，区分用户命令、内部校准和真实中断。
2. 来电类 pause 中断结束直接调用 `play()`，没有记录中断前是否应播放。要防止恢复用户主动暂停的会话。
3. duck 中断结束把音量写回 1.0，不能恢复用户之前的 A/B 输出音量。应保存实际输出音量，并与中断期间用户的新操作协调。

后台策略建议明确区分三种状态：

- 应用仍可见或在系统 PiP：保持可见视频，允许双流，暂停不必要的校准编辑。
- 完全后台/锁屏且用户允许后台播放：继续 B 音频，停止不需要的视频输出和弹幕绘制；根据各平台能力释放视频解码资源。A 是否保留时钟推进或需要重开必须实测，不能隐藏 Widget 就宣称关闭解码。
- 不允许后台播放：两路一起暂停；回前台只恢复原先应播放的会话，不擅自清除用户暂停。

后台改变了任一路时钟连续性时，回前台重建基线、重新应用偏移，并允许再次校准。保留 iOS 所需的音频会话，不靠在后台继续渲染视频维持存活。

### 控制双流资源开销

B 在校准或裁剪覆盖时才需要视频。现有 `needsCompanionVideo` 和串行视频轨切换可以复用：结束校准且没有覆盖时真正关 B 视频轨；开启覆盖时保留最低可用画质；退出释放实例和监听。

关视频轨减少解码和渲染，不必然减少原始直播 URL 下载的视频字节。资源记录需区分网络流量、压缩缓存、解码器和 Flutter 绘制。Android 低端设备的双硬解能力、iPhone 长时间发热降频，要分别验证；不能从单路硬解流畅直接推定双视频长期低功耗。

系统 PiP 与应用内裁剪小窗是不同功能。[buildPiPOverlay](../lib/player/core/player_manager.dart) 当前仅组合 A 和紧凑弹幕，B 裁剪层在普通播放器控制面板里。Android PiP 要明确接入 B 层及恢复生命周期；iOS 系统 PiP 还需原生输出方案，单独做能力验证，不列为首批已支持。

## 3. 交付顺序与验收

每步独立提交和回归；保留全部现有功能，不顺带升级内核或全量合并另一项目。

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| R1：恢复可靠性 | 适配 A 的直播 EOF/新地址恢复；核查斗鱼静默断开证据 | EOF/error 合并、用户暂停/下播/切房不误重试，双流偏移和弹幕来源保留；静默超时结论有对应证据 |
| M1：共享移动基础 | 双流引擎会话约束、系统状态/中断修复、响应式校准与触摸裁剪 | 假播放器/可控时钟测试与手机/iPad 尺寸组件测试通过，桌面原路径回归通过 |
| M2：Android 前台测试版 | 开放手机双流入口，A/B 音画、校准、弹幕、裁剪覆盖、全屏 | GitHub Android arm64 构建；实测可随时再校准、换 B、退出，无灰屏或残留声音 |
| M3：iPad → iPhone 前台测试版 | MediaKit 实际解码验证，分屏/旋转/安全区、签名与安装链路 | GitHub iOS 构建，并按可用签名方式交付；实机验证而非只有编译通过 |
| M4：后台与系统 PiP | 先两平台后台音频，再 Android PiP；iOS 原生 PiP 单独验证 | 来电/蓝牙/锁屏/切网后状态一致，回前台恢复选定弹幕和偏移，无重复纹理或解码器泄漏 |

优先 Android 的原因是已有默认 MediaKit、硬解和 APK 交付链路。iPad 先于 iPhone 是为了先验证双播放器和较宽松的校准布局，手机的小屏交互在共享基础阶段就要设计，不能最后简单缩放。

测试重点：

- A 单流 → 启动 B → 隐藏/重开预览 → 裁剪 → 拖动 → 退出，反复 20 次；结束后实例、监听、计时器不累积。
- 玩机器作为 B，至少一组同平台、一组跨平台 A/B；分别测试 B 无音轨/掉线、A 重签名/换画质/换线路、暂停中重连。
- 弹幕 A/B 切换、选 B 后调整偏移、离开再进、断线时后台再返回，继续保留 15 秒重连。弹幕负偏移不能提前显示尚未收到的消息。
- 竖屏/横屏、iPad 分屏、覆盖边界、确认/取消、亮度/音量手势，以及后台禁用设置。
- 来电前已暂停、播放中来电、duck 前非满音量、耳机拔出、锁屏控制；系统状态不得被 10ms 校准暂时暂停误改。
- 同一设备同一流分别测单流、B 纯音频、双画面校准、裁剪覆盖，记录实际解码器、画面掉帧、内存和温度变化。稳定网络连续 30 分钟观察相对基线漂移，约 200ms 是验收目标，尚非本次实测结论。

构建继续走 GitHub Actions，按平台依次出测试包，不占用本地做应用打包。当前 workflow 已有 Android arm64 APK，以及 iOS unsigned app/TrollStore IPA；后者不能当作普通 iPhone 可直接安装的正式包。正常设备分发需要匹配的开发/Ad Hoc/TestFlight 签名链路。

iOS 工程另有部署目标不一致：Podfile 为 15.0，项目基础配置为 15.6，ShareExtension 为 18.2。迁移前需核对各 target 的有效设置、依赖要求和打包产物；不能据其中一个数字宣称完整包的最低系统版本。这里不通过删除已有分享功能来简化交付。
