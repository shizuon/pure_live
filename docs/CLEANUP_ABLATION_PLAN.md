# 全功能保留的清理与性能消融计划

2026-09-10，代码基线：`fec2af10bd976dbaa9dfe39c7ad01683bcbde0a9`，版本 `3.0.17+4105`。

本文记录源码审查和实验规划，E1—E8 尚未实施。随后进行的桌面卡顿采样及 3.0.18 候选改动另见 [桌面播放卡顿排查](DESKTOP_PLAYBACK_STUTTER.md)。用户已明确：**保留现有全部功能，只清理重复代码和不必要的后台开销。** macOS 和 Windows 通过 GitHub 构建，其他平台保留兼容性。

可以做，而且已经找到具体切入点。优先级是：减少启动和进房的多余工作 → 缩短 B 首次出声的等待 → 收敛闲置资源 → 清理依赖和重复实现。每项单独比较，避免把多个变化混在一起后无法判断收益和回归来源。

## 已确认的代码路径

| 项目 | 证据与影响 | 建议 |
| --- | --- | --- |
| 普通直播页提前创建录制服务 | `LivePlayController` 的字段直接 `Get.find<RecorderController>()`。录制设置随之初始化存储并统计目录；录制服务注册一分钟周期 Timer、FFmpeg 事件订阅并恢复任务。 | 拆开轻量任务状态与执行服务；无任务时，展示录制按钮不应启动完整服务。 |
| 桌面端无条件预热 FFmpeg | `AppInitializer` 在首帧后两秒调用 `FFmpegManager.initialize()`；最终进入原生 `FFmpegKitExtended.initialize()`。 | 桌面按首次录制/处理任务初始化，并合并并发调用；保留自动恢复任务需要的初始化。Android 的首次录制历史兼容策略单独保留。 |
| B 首播等待全部画质解析 | `StreamSourceResolver.buildCandidates()` 对所有画质顺序 `await getPlayUrls()`，完成后控制器才尝试第一条候选。 | 按画质惰性解析：最低档可用即播放；同档线路失败后才请求下一档。保留去重、请求头、重连重新签名和全部可用线路。 |
| 设置生命周期重复调度 | `SettingsService.lockInject()` 串行等待 200ms 后手动调用 `onReady()`，而本地 GetX 的 `onInit()` 已安排首帧后调用。当前这些设置类未发现 `onReady()` 覆写。 | 删除额外生命周期调度，必要的异步初始化使用显式 Future。主要消除多余任务和生命周期歧义，不能宣称省下同等长度的冷启动等待。 |
| IPTV 设置重复注册 | 同一类型先 `lazyPut`，后 `put(IptvSettingsController(), permanent: true)`；本地 GetX 对已有干净注册直接返回。 | 只保留一种有明确生命周期的注册。现状会多构造一个临时对象，不能据此声称两个控制器都在执行同步。 |
| IPTV 启动强制导入 | 平台启用时，三秒后调用热门列表和默认 EPG 导入，两者都传 `forceUpdate: true`；这两项不受 `isAutoSyncEnabled` 控制。 | 复用本地数据并按有效期/缺失情况更新，合并同源在途请求。首次导入、手动强刷、已有自动更新设置必须仍有效。 |
| 隐藏控制栏仍有时钟 Timer | 全屏顶部栏通过移出画面隐藏，`DatetimeInfo` 仍每十秒 `setState`，只显示小时和分钟。 | 隐藏后停止时钟更新；显示时立即刷新，再对齐下一分钟。收益较小，适合作为低风险实验。 |
| 表情按整个平台预解码 | `EmojiManager.preload()` 已分批、去重并下采样至 24×24，但切平台仍先完整预解码；`release()` 未找到应用调用点。 | 先测切平台耗时和 atlas 留存；尝试按实际表情加载或在最后一个消费者退出后释放。需要覆盖多画面和悬浮窗的所有权。 |

录制缓存限制默认关闭。因此，无任务时周期 Timer 的唤醒是确定存在的；“每分钟扫描目录”只在用户开启限制时成立。首次创建录制设置时的目录统计则是另一路开销。

数据库使用 `LazyDatabase`：启动创建 `DbService` 不等于立即打开 SQLite 或创建后台 isolate。真正应查的是第一次查询由谁触发，不能仅改成 `lazyPut` 就宣称数据库开销已消除。

## 已有优化需要保留

- 主播放器在首次进房时才创建原生媒体资源，退出直播页会卸载媒体；保留空播放器对象不等于还在拉流。
- B 校准结束且没有裁剪覆盖时，已有关闭视频轨的调用；再次校准、裁剪和覆盖会按需恢复。不能把现在的 B 一概当作后台持续视频解码。
- A/B 弹幕切换由一个 `DanmakuController` 管理当前连接，没有必要为了“合并两条弹幕连接”另起改造。
- 弹幕已有队列上限、过期淘汰、消息批处理、布局缓存与空闲停止的 Ticker；图片已有内存上限，关注核验已有有界并发。
- 两秒一次的双流漂移检测、WebSocket 心跳和十五秒重连承担实际功能，不应作为无用 Timer 删除。
- 当前 macOS 强制软件解码与此前 HDR/窗口闪烁的稳定性取舍有关，不能直接恢复硬解作为本批清理。
- 不能为了少一个对象，把用于不同显示位置的 Video Widget 缓存复用；此前裁剪灰屏正与显示 Widget 的订阅生命周期有关。

## 包体和依赖：哪些值得动

删除代码行通常先减少维护成本。Flutter release 会裁剪未使用的 Dart 代码，但资源和原生插件不完全遵循同样的裁剪方式。安装包、安装后磁盘、实际内存和 CPU 需要分别测量。

只读盘点了本地历史 `3.0.7+4095` 的 macOS `.app`，按文件逻辑字节统计、不重复计算符号链接：

| 部件 | 历史包中的大小 | 能否直接删除 |
| --- | ---: | --- |
| `ffmpegkit.framework` | 47.32 MiB | 不能，录制和媒体处理仍使用它。 |
| `grpc.framework` | 27.29 MiB | 不能单独删除，是云端功能原生依赖链的一部分。 |
| `FirebaseFirestoreInternal.framework` | 11.27 MiB | 不能，保留云同步功能。 |
| `FlutterMacOS.framework` | 29.44 MiB | 不能，是应用运行时。 |
| `App.framework`，包含其资源 | 56.65 MiB | 需要进一步按编译代码与资源拆分，不能整体当作业务代码。 |

这些只是识别大依赖的历史样本，**不是当前 3.0.17 的包体测量，更不是运行内存或可回收空间**。后续从同一轮 Actions 产物重新测基线。

当前源码 `assets/emo` 约 19.86 MiB，但 pubspec 只显式打包四个平台的图片目录；源码目录总量不能当作最终安装包贡献。对该源码目录按 SHA-256 盘点，完全相同的内容只有四组，可去重约 35,405 字节，单靠去重表情文件收益很小。

在 `lib/test/tool` 的 Dart import/export 中没有找到以下直接依赖的引用：`hashlib`、`crypto_simple`、`lottie`、`bordered_text`、`font_awesome_flutter`、`timezone`、`quiver`、`animated_splash_plus`、`app_links`。它们是待核验的清理候选，**不是已证明安全的删除列表**。还需查原生注册、配置/生成器、插件内部引用和全平台功能入口，尤其是 `app_links` 与登录回调。

`file` 和 `html` 虽然没有应用直接导入，但仍被缓存、分享或 HTML 渲染等依赖使用；删掉直接声明不会让它们从依赖树消失。`media_kit_libs_video`、`audio_service_win` 等通过插件机制工作，不能按无 Dart import 删除。`waterfall_flow` 仍用于历史、收藏分区和账号页面，也不是死依赖。

保留全功能时的包体实验顺序：

1. 清理经过核验的无用直接依赖和仅由它们带入的资源，固定其他依赖版本后比较产物。
2. 检查 FFmpegKit `small` 变体是否保留现有协议、TLS、解码器、封装器和过滤器；不预设 `base + small` 一定有收益，也不删掉 MediaKit 的 FFmpeg 库来强行共享 ABI。
3. 如需减少单次下载，可另提供 macOS arm64/x64 包，同时保留原有 universal 包。它减少下载/磁盘体积，不自动减少当前进程内存。

Firebase、WebView、录制、IPTV、投屏、多画面、备用播放器以及跨平台目录均保留。删除这些会越过本次范围。

## 消融顺序与验收

先在 `fec2af10` 上建立基线，再从同一基线分别做各实验。独立收益确认后才组合；不要拿“已经叠加六项修改”的包与旧包比较后给每项分配收益。

| 实验 | 单一改动 | 主要观察项 | 必须守住的行为 |
| --- | --- | --- | --- |
| E1 | 取消设置的手工 `onReady` 排队，统一 IPTV 注册 | 生命周期调用数、启动 Timer 数、首次设置页耗时 | 首次安装、旧设置迁移、字体、备份恢复都正常；每实例生命周期只触发一次。 |
| E2 | 桌面 FFmpeg 按使用初始化 | 首页闲置 CPU/内存、线程数、首次录制延迟 | 首次录制成功，自动恢复任务正常；失败可重试，并发只初始化一次。 |
| E3 | 录制状态与执行服务分离，资源扫描按目录变动/实际任务触发 | 无录制进房时的目录扫描、常驻 Timer、重返首页后的留存 | 按钮状态正确；录制、轮询待开播、续录、缓存限制和任务恢复不漏执行。已有磁盘数据在启动或相关入口仍需核验。 |
| E4 | B 按需解析画质候选 | B 首次出声耗时、URL 解析调用数、取消后继续工作的数量 | 同画质逐线路回退、再升级画质，URL 过期重新获取；B 未就绪时仍听 A。 |
| E5 | IPTV 默认资源复用、合并相同导入请求 | 重复启动的网络字节数、XML 解析/数据库写入、首屏竞争 | 冷安装有默认资源，手动更新立即执行，已有自动同步不失效。 |
| E6 | 控制栏隐藏后暂停纯展示更新 | 控件重建数、闲置唤醒数 | 再次移入时立即显示正确时间；播放、声音和覆盖画面不被停止。 |
| E7 | 表情按需解析/有界保留，明确最后消费者释放 | 首条弹幕等待、切平台 CPU、atlas 内存、切房内存趋势 | 首次表情可见，多画面跨平台表情正确，悬浮窗仍有效，无已释放图片被绘制。 |
| E8 | 清理核验过的死依赖 | 新安装包与安装目录字节数、构建依赖数 | 登录、平台签名、备用引擎、系统媒体键等原生入口不缺失。 |

首批建议只做 **E1—E4**，分别提交，分别保留比较记录。E6 很小，可以独立穿插。E5、E7 需要更多数据与多消费者生命周期测试。

设置额外回调、控制栏时钟、无任务 Timer 的收益可能很小，应如实记录。若性能改善低于运行间波动，只能把收益写成减少冗余/维护成本，不能宣传成明显提速。

## 后置实验与代码归并

**硬件解码**可能比删零散代码更影响高分辨率视频 CPU，但需要另起实验：对比当前软件解码、VideoToolbox 可用路径及失败回退，覆盖 SDR/HDR、窗口/全屏、A 单播、B 预览/裁剪覆盖。出现闪烁、灰屏、崩溃即回滚，不能仅因 CPU 下降就采用。

**B 缓冲预算**目前继承直播默认前向 32 MiB、回看 4 MiB 的上限；上限不等于实际分配。是否可按 B 码率缩小，需要单独验证弱网及 ±30 秒校准。减小缓存可能使长暂停后无法追上或出现断流，不能直接套固定小数值。

**源码归并**优先收敛共同的请求头解析、房间身份、取消/释放语义；A 首选画质、B 最低画质和录制的选择策略继续分离。当前 B 已复用 `PlaybackHeaderResolver`，无需再造一个重复层。

`PlayerPool.getPlayer()` 的缓存只在异步创建完成后写入，池自身没有合并在途创建；是否会泄漏取决于上层并发调用。后续生命周期测试应覆盖并发获取、获取中退出和销毁失败，然后再决定增加在途 Future 与明确所有权。未复现前不把它写成已发生的播放器泄漏。

`video_controller_panel.dart` 约 2,226 行、`player_manager.dart` 约 1,913 行，适合按控制栏、呈现模式和播放会话拆分以降低修改风险。单纯拆文件不会提高帧率。GetX 本地修复、MediaKit Video 本地补丁、Drift/Protobuf 生成代码和第三方许可证声明不作为删行目标。

## 测量方法与退出条件

Actions 负责构建、依赖/包体审计和自动化测试；CI 虚拟机上的播放性能不能代替用户 Mac 或 Windows 设备的帧率、HDR和功耗结果。

| 场景 | 采样安排 | 指标 |
| --- | --- | --- |
| 冷启动到首页，停留 60 秒 | 同一配置重复至少五次，区分冷/热缓存 | 首帧与首页可交互耗时、CPU、进程内存、线程、Timer/请求数。 |
| A 普通播放 | 固定源与清晰度，预热后采样五分钟 | 丢帧、Flutter build/raster p95/p99、CPU、内存、解码与纹理数量。 |
| A+B，完成校准并隐藏 B 视频 | 与 A 单播对照，再稳定播放三十分钟 | 两路资源数、B 视频轨确已停用、相对同步漂移、网络字节数。 |
| 再次校准 → 裁剪 → 覆盖 → 关闭覆盖 | 重复切换二十次 | 无第三个残留播放器，无灰屏；音量、裁剪位置和偏移保持正确。 |
| 海量弹幕与切 A/B 弹幕源 | 使用同一条带时间间隔的消息回放，再补真实房间 | 消息到呈现的延迟、过期丢弃、主线程耗时、隐藏时的重绘；不通过少显示弹幕伪造收益。 |
| 玩机器 → 其他房间 → 玩机器 → 首页 | 重复三十轮，在相同空闲点记录 | 原生播放器/连接/订阅/纹理是否回到预期数量，内存是否趋于稳定，十五秒重连仍执行。 |
| 录制、IPTV、登录同步等低频功能 | 首次使用、再次使用、旧数据恢复 | 首次使用延迟及成功率，功能不因延迟初始化而失效。 |

同一设备、分辨率、HDR/刷新率、窗口尺寸、音量和缓存条件下比较。先用可重复的本地媒体及弹幕回放隔离 CDN 变化，再检查真实斗鱼/虎牙。测试素材可以是临时生成的测试信号，不需要录制用户直播内容。

内存记录需区分 Dart heap、进程常驻/私有内存和原生资源；macOS、Windows 指标各自比较，不能把工作集与 Dart heap 混成一个数。release 包用于实际占用和播放体验，profile 包用于耗时定位，两种构建的数字不直接互比。

每项保留基线/实验 SHA、平台、采样配置、重复次数、原始记录及中位数/分位数。资源计数和回归测试先证明少做了什么，再确认是否改善用户可见指标。循环退出后资源数量继续增长、增加无声/灰屏/重连故障、破坏录制或旧数据，都立即否决该实验。

通过的实验组合后，再跑完整核心流程及受影响外围功能的回归。没有可重复收益且增加复杂度的实验不合入。E1—E8 后续单独推进；3.0.18 桌面卡顿候选沿用现有测试分支并保留斗鱼重连修复，构建跟进需延续至最新候选产物交付。
