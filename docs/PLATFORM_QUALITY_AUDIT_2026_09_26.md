# 其他直播平台：高画质请求、实际流与帧率核查

2026-09-26；源码 `8321f02f`（包含斗鱼网页登录和实际画质回传）。
用户要求检查其他平台是否也存在斗鱼“选1080P60、实际约30帧”的情况。
本轮检查12个平台的取流路径，不修改应用源码，不影响正在构建的3.0.24 Mac。

## 证据口径

- 匿名公开接口：B站、YY、虎牙元数据由Python请求；虎牙、Twitch、Kick、
  YouTube另使用当前Dart生产适配器，临时空Hive配置、无真实账号Cookie。
- 每条媒体仅采约5秒包时间戳，ffprobe不保存视频，不运行播放器。
  包DTS平均间隔不是屏幕实际呈现FPS，也不证明长时间无卡顿。
- `r_frame_rate`、`avg_frame_rate`、包时间戳可能不一致。例如B站第二个样本
  r_frame_rate为59.94，实际短时包平均约30.38，不能单看一个字段宣布60帧。
- 六个确定性测试是对**现有缺陷的特征复现**，通过表示复现成立，不表示已修复。
  所有原始签名URL、会话及取流响应只在忽略目录，不进入文档或提交。

## 逐平台代码判断与修复优先级

| 平台 | 当前机制 | 风险与处置 |
| --- | --- | --- |
| 斗鱼 | 3.0.24回传实际rate、按档分组；官方网页登录 | 正在单独构建交付，真实账号和长期60fps待验证 |
| B站 | 读取current_qn、同确认档线路分组 | 常规降档已正确回传。实际qn若不在旧菜单，消费层仍回退请求标签；夹具已复现，P1修补菜单外确认状态 |
| YY | 桌面StreamManager失败转移动HLS，接口返回宽高 | **确定的同类标签错误**：原画请求→360P HLS，统一接口却确认原画；夹具复现，P1为回退源生成实际描述并贯穿A/B/录制 |
| 抖音 | sdk_key对应清单URL，无额外画质协商 | **确定的账号会话错误**：静态Cookie先于设置，新登录可能继续用匿名缓存，清除后也可能保留旧会话；夹具复现，P1修登录/退出一致性。没有证明此问题已导致特定房间降帧 |
| 快手 | 一旦有H.264 representation，就不读HEVC组 | HEVC专属最高档可能丢失；夹具复现，P2按档选择编码，不是整组丢弃。尚无真实房间证明遗漏60帧 |
| 虎牙 | 元数据列画质，签名URL携ratio；原画去掉ratio | 无独立实际rate确认；当前抽样60帧正常。保持既有签名和硬解，不因理论可能性重写 |
| Twitch | HLS STREAM-INF与URI配对，保留FRAME-RATE | 正常样本60帧。共用解析器缺分辨率时按码率猜标签；P2应显示码率/未知而非猜1080P |
| Kick | 复用HLS解析器；媒体清单无分档时标原画 | 同上；媒体清单不一定证明源画质，不应把“单一可播放流”当最高档证据 |
| YouTube | Android客户端提供的HLS变体，不使用视频单轨 | 正常样本29.97帧；该接口给出的最高档不等于网页所有编码的最高档。未证明有缺失的更高变体 |
| 网易CC | 按平台质量key绑定CDN URL | 未发现斗鱼式二次请求确认丢失。尚未媒体抽样，不宣称实际FPS一致 |
| SOOP | VIEWPRESET名字请求CDN和AID，未检查媒体确认 | 存在元数据与最终媒体未核对的证据缺口；尚未复现实际降档，不盲目加登录或重试 |
| IPTV | 导入URL，仅显示“默认” | 不伪称原画；若URL是自适应主清单，实际分档由播放器选择，当前不展示选中变体 |

HLS另一项夹具复现：相同高度/四舍五入FPS/码率/VIDEO字段、不同CODECS
会被合并成线路。它影响硬解兼容和线路身份，**不等于已证明降帧**。
协议中码率与分辨率是独立属性，参考 [RFC 8216 §4.3.4.2](https://www.rfc-editor.org/rfc/rfc8216#section-4.3.4.2)。
