# 桌面播放卡顿排查：Windows 帧交付与 macOS 软件输出

2026-09-10。代码基线 `fec2af10bd976dbaa9dfe39c7ad01683bcbde0a9`，候选版本 `3.0.18+4106`。

用户反馈分为三项：他人疑似 Windows 副屏全屏后逐帧播放；用户自己的 Mac 在播放器部分可见、操作其他 App 时卡顿；播放一段时间后偶发卡几下再恢复。房间为斗鱼玩机器。用户补充：声音大多连续，画面严重卡顿时声音偶尔也卡；画面最断续。其他人的操作系统尚未独立确认，画质和线路尚待补充，不能把三项直接认定为同一个问题。

## Windows：存在确定的帧交付饥饿问题

来源分类为 `upstream-existing`：当前 `third_party/media_kit_video/windows/mailbox_swap_chain.cc` 与冻结的上游 `b97ed3ed628e6bf9dfacd96be3b4418da40eb966` 在修改前没有差异。它是所有平台直播共用的 Windows 呈现路径，不能只称为斗鱼接口故障。

旧代码每渲染一帧，检查上一帧 GPU fence 是否完成，然后无论结果如何都把 pending 替换成这一帧。若 GPU 完成需要超过一个渲染间隔，程序就永远检查刚提交、尚未完成的帧，之前完成的帧失去跟踪；Flutter 一直拿到旧的 completed 画面。GPU 偶尔及时完成时又能前进，足以产生时停时走的表现。

对旧算法进行 120 次提交的时序模拟：延迟一帧时可更新 119 次；延迟两帧及以上时更新零次。这证明了算法缺陷，**不等于已在反馈者的副屏上复现**。

修正将四个纹理槽位的状态提取成 [MailboxFrameState](../third_party/media_kit_video/windows/mailbox_frame_state.h)：未完成的 pending 始终保留，生产者可继续在自己的 write 槽位渲染；确认 fence 完成后才发布，并轮换槽位。消费者仍只进行一次原子读取，不增加 Flutter 渲染线程的 GPU 等待、Sleep 或刷新重开。

实际生产代码使用的状态类由 [原生回归测试](../test/native/mailbox_frame_state_test.cpp) 覆盖：固定 GPU 延迟 1/2/3/5/20 帧、快慢负载切换、单调交付、不覆盖当前显示/pending 槽位、重置。120 次提交分别交付 119/59/39/23/5 次。延迟本身仍会影响帧率；修复的是“已完成帧持续无法交付”。

测试已用本机 C++ 编译器运行，且接入两份 GitHub 构建工作流的质量阶段。DXGI 原生编译、真实 GPU、跨显卡/刷新率的副屏和纹理 resize/退出仍需 Windows 构建及实机验证。此测试不覆盖驱动层行为。

## macOS：采样显示软件图像转换占用明显

只读采样了用户当时正在运行的 `/Applications/纯粹直播.app`，没有启动、切换或安装应用：

- 版本 `3.0.16 (4104)`，ARM64，macOS `27.0 (26A428)`。
- `ps` 当时的进程 CPU 为 `122.5%`（单个逻辑核心为 100%），RSS 约 279 MiB。
- 三秒线程采样记录 physical footprint 为 510.7 MiB；它与 RSS 是不同统计口径，不能混比。
- 视频 Worker 的 272 次线程采样中，268 次落在 `TextureSW.render → mpv_render_context_render → Swscale` 的转换路径；主线程 272 次采样中有 240 次在事件等待。

这次采样定位了当时的重要负载，不能证明采样窗口恰好覆盖用户感受到的卡顿，也不能把线程采样比例当作整机 CPU 比例。原始采样保留在本机临时路径 `/private/tmp/pure-live-stutter-sample.txt`，不上传完整系统报告。

代码核查：当前 Mac 同时强制 `hwdec=no` 和 `enableHardwareAcceleration=false`。该策略在上述冻结上游也存在。视频 Widget 的 `pauseUponEnteringBackgroundMode` 为 false，没有发现因普通窗口失焦而直接暂停播放的代码。本机没有针对 App Nap、遮挡状态或网络缓冲进行对照复现，因此这些因素仍未排除。

首个低风险候选改动：把已有的 Windows 视口尺寸控制复用到 Mac 的 `BoxFit.contain` 显示，按实际控件尺寸 × DPR 限制软件 BGRA 输出，并在窗口变化稳定 180ms 后更新。全屏仍可恢复源分辨率；其他 fit 在 Mac 继续使用源尺寸，避免裁剪/填充细节下降。没有改变直播清晰度、音量、B 视频轨策略、HDR 合成设置或软件解码选择。

这只在实际显示尺寸小于源画面时减少转换工作。窗口被其他 App 遮住一部分但尺寸没变，不会按被遮挡比例缩小；大窗口/全屏下也不能保证减少负载。修改后的 CPU 和卡顿情况尚未采样，不宣称已经修好后台卡顿。

共享的 [视口控件](../lib/player/widgets/viewport_sized_video.dart) 保持挂载，在 Mac 切换为裁剪/填充时撤销尺寸覆盖，让原生输出继续跟随源尺寸。另修复快速全屏往返留下旧 resize 计时器的问题：返回已应用尺寸时也取消待执行请求，防止稍后被过期尺寸覆盖。

进一步方向是分别测软件解码、软件输出以及安全的硬解回拷路径，避免把“恢复硬解”与“恢复曾闪烁的 OpenGL 输出”绑在一起。当前候选不改变这两项。

## 弹幕负载与隐藏状态

本次采样中 Flutter raster 线程 272 次采样里有 246 次在事件等待。结合软件视频输出的热点，暂时没有证据把弹幕作为当时主要瓶颈，但这不能排除弹幕爆发时的瞬时负载。

主画面已有 48 条同屏、120 条排队、五秒过期、50ms 入场间隔以及有界文字/绘图缓存。Flame 的 `GameWidget` 默认有独立重绘边界；引擎在清空、未挂载、hidden/paused 后停止自有 Ticker，窗口 inactive 但仍可见时继续正常绘制。历史列表还有 64ms 接收合并与 80ms 视图批处理。

发现主画面用 `Offstage` 隐藏弹幕时仍保留整个绘制引擎。普通隐藏后现有消息消失前仍有推进；竖屏隐藏策略更可能持续接收消息并做不可见的工作。此项在冻结上游也使用同一 Offstage 结构，属于 `upstream-existing`。候选改成与现有小窗一致的条件卸载：隐藏/关闭显示时移除绘制 Widget，立即清理 Ticker/缓存；连接和历史列表仍由直播控制器管理，重新显示后绘制新消息。它改善的是隐藏状态，并非降低正常可见弹幕的数量或帧率。

## 偶发卡顿：还不能定性为网络问题

正常拉流线程也会等待网络数据，单次线程采样不足以证明 CDN 卡住。需要同一故障时间窗的缓冲水位、播放位置、丢帧数和音频状态：

| 故障时信号 | 下一步 |
| --- | --- |
| 音频连续，缓存充足，视频交付/丢帧异常 | 优先检查上述呈现问题、软件转换耗时或 GPU 帧提交。 |
| 音视频一起停，缓冲水位耗尽，播放器进入 buffering | 核查当前线路的分片/FLV 到达间隔与吞吐，再判断缓存策略。 |
| 仅弹幕卡顿，媒体时钟连续 | 单独看弹幕布局、历史列表与回放队列。 |

当前没有足够的时间序列证据支持改协议、换线路、扩大缓存或全局禁止后台省电；这些设置本次不动。底层 MediaKit 默认启用了 `cache-on-disk`，应用另设前向 32 MiB、回看 4 MiB、预读两秒；它们也是后续需要分开测量的变量，不能直接认定为故障原因。

## 验证与回滚

本机定向测试通过：输出尺寸与 Mac 兼容策略 5 项；弹幕队列与历史列表 20 项；补充的视口切换/销毁和弹幕卸载/重挂载测试通过（与已跑弹幕测试有重叠，共 27 项不同测试）。C++ 帧状态回归通过。Dart 定向分析未发现错误或警告；提取公开控件后提示的 `key` 建议已补齐。完整质量检查和两个平台的原生编译交给 GitHub Actions，完成结果以对应运行记录为准。

候选包应保留 `3.0.17` 的斗鱼切房后十五秒弹幕重连修复、双流、10/100/500ms 校准、A/B 弹幕、裁剪覆盖和退出清理。

- Windows：同一线路分别测试主屏窗口、副屏窗口、副屏全屏；涵盖不同缩放/刷新率、启用与关闭 B、GPU 被其他 App 使用、全屏往返和退出。
- Mac：同一画质/线路比较播放器前台、部分遮挡、全屏；观察声音是否连续，记录帧率与 CPU，同时验证 HDR 无闪烁、再次校准和裁剪覆盖。
- 新包先作为测试构建，不以自动化测试通过替代副屏/HDR 验收。若新灰屏、花屏、退出崩溃或音频回归，回滚相应平台改动；Windows 帧状态和 Mac 视口改动互相独立。

全功能保留的代码清理规划另见 [性能消融计划](CLEANUP_ABLATION_PLAN.md)。它的 E1—E8 尚未整体实施；本批仅包含这里列出的呈现修复、Mac 视口候选优化和隐藏弹幕清理，不能把其他规划算进修复收益。
